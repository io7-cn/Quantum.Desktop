# Desktop data acceptance

[简体中文](../zh-CN/desktop-data-validation.md) · [Installation and updates](desktop-releases.md) · [Issue #8](https://github.com/io7-cn/Quantum.Desktop/issues/8)

Use a disposable Windows account or VM and synthetic records. Record the candidate commit, package SHA-256, Windows version, installation path, results and screenshots of both confirmation dialogs. Do not use a real user's database. The repository's `test` and `windows` checks remain required; automated filesystem and PowerShell orchestration tests do not replace this package-level acceptance.

1. Install the candidate at the default location and launch it. Confirm the generated MAUI publisher is `io7-cn` and that databases, personal plugins, logs, preferences and secure state are written outside the installation, under `%LOCALAPPDATA%\io7-cn\io.quantum.desktop`. Install a plugin and save a recognizable record and language preference.
2. Use Windows Settings to uninstall. Confirm the default choice is to keep data, the displayed path is correct, and Cancel leaves the app installed. Repeat with Keep, wait for successful uninstall, reinstall and verify the record, plugin, preference and sign-in state remain available.
3. Repeat with Delete. Verify the second confirmation defaults to declining deletion. Decline and confirm the installation remains. Confirm deletion on another attempt; verify both fixed data roots are gone and a reinstallation starts clean. Put a sentinel in an external `QUANTUM_MODULES_PATH` and verify it survives.
4. Run the registered `QuietUninstallString`. Confirm there are no data dialogs, data survives and reinstallation restores the record. Simulate an updater failure and confirm data remains; restore the candidate before continuing.
5. Seed the old root `%LOCALAPPDATA%\Quantum\io.quantum.desktop` with settings, protected state and a SQLite database with committed WAL records. Seed `current\Modules` with a plugin and disabled plugin. Close the old app and back up both locations outside the installation before installing the candidate. Follow the transition instructions in the release guide for plugins removed by the old updater. Launch, confirm migrated records and plugin behavior, and confirm originals were not changed. Change a record in the new root and relaunch; stale legacy data must not be replayed.
6. Repeat migration with conflicting plugin files, an invalid database, an unreadable source and an existing nonempty destination without the completion marker. Startup must stop visibly without publishing partial or empty replacement data. Resolve the problem and retry. Check a junction in either a source or destination ancestor is rejected. Confirm a legacy-only installation with a failed migration cannot be removed through the registered wrapper until migration is resolved.
7. Update the successfully migrated candidate to a second test package. Verify data and plugins survive, the post-update hook refreshes the uninstall choice entry even before normal app startup, and uninstall/reinstall still works. Also test a custom installation location. Verify the published package contains `Uninstall.ps1` next to `Quantum.exe`.

The acceptance owner records evidence in the issue and PR. Keep the issue open until independent review, required CI and this installation acceptance pass. macOS uses its existing system data locations; removing an `.app` retains those locations and does not run the Windows uninstaller.

If a candidate needs rollback, keep and back up the new data root. Original legacy copies are retained for diagnosis, but become stale once the new app writes data; do not silently switch back to them or overwrite newer records. Restore a verified backup through an explicit recovery procedure.
